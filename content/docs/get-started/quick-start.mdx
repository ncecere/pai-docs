title: Quick start

The quickest way to see Pi Agent Interface working is to run it on your machine with its built-in **development accounts** (Tim, Bob and Sally, no password) and point it at a Pi Durable platform. Each development account connects a platform account and gets its own agents there, so you can see how people are kept apart.

<Callout type="warn" title="For your machine only">
  The development accounts work only when the app's address (`APP_URL`) is `localhost`, `127.0.0.1` or `[::1]`: the server refuses to start otherwise. This setup is a way to look around, not a production install. See [Operate](/docs/operate) for that.
</Callout>

## What you need

- **A Pi Durable platform that offers Connect** (it advertises `connect` in `GET /v1/auth/config`), with personal workspaces on, and an account on it for each person you will sign in as. This is the default mode, and the one this guide uses. Because the app runs on `localhost`, it registers itself with the platform; the platform must offer client registration for that. See [The agent platform](/docs/operate/platform#connect-mode).
- Or, for a platform without Connect, a **team** (this guide's alternative uses the slug `pi-agent-interface`) with a **service account** of role **editor**, its key (`pdp_sa_…`), and preferably a **model published to the team**. Without a model, every agent answers from the platform's default, which out of the box is a scripted demo model.
- **Docker** with Compose v2, and **Git**.
- For the source route: **Node.js 22** and **pnpm** (the version in the repository's `package.json`, through `corepack enable`).

## With Docker Compose

This runs the app and its PostgreSQL in containers, using the published image.

<Steps>
<Step>

### Write a Compose file for the app and its database

Save this as `compose.local.yaml`:

```yaml title="compose.local.yaml"
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: pai
      POSTGRES_PASSWORD: pai-local-only
      POSTGRES_DB: pai
    volumes:
      - pai-local-db:/var/lib/postgresql/data
    healthcheck:
      test: [CMD-SHELL, pg_isready -U pai]
      interval: 2s
      timeout: 3s
      retries: 20

  app:
    image: ghcr.io/ncecere/pi-agent-interface:v0.3.0
    depends_on:
      db:
        condition: service_healthy
    ports:
      - 127.0.0.1:8080:8080
    env_file: .env.local
    environment:
      APP_URL: http://localhost:8080
      DATABASE_URL: postgres://pai:pai-local-only@db:5432/pai
      DEV_AUTH: "true"

volumes:
  pai-local-db:
```

</Step>
<Step>

### Write `.env.local`

Fill in your platform's address, and generate a session secret:

```sh
cat > .env.local <<EOF
PLATFORM_URL=https://agents.example.com
PLATFORM_AUTH=connect
CONNECT_EMAIL_MATCH=off
SESSION_SECRET=$(openssl rand -base64 48)
INITIAL_ADMIN_EMAIL=tim@example.test
EOF
```

`INITIAL_ADMIN_EMAIL=tim@example.test` makes Tim the first administrator when he signs in, so you can look at the admin dashboard too. `CONNECT_EMAIL_MATCH=off` is needed here: the development accounts' emails (`tim@example.test`) are not your platform account's, and the app would otherwise refuse the connection (see [the account check](/docs/use/connect-your-platform-account#the-account-check)).

<Callout title="With a service account instead">
  For a platform without Connect, use these lines in place of the three platform lines above: `PLATFORM_AUTH=service`, `PLATFORM_TEAM=pi-agent-interface`, `PLATFORM_SERVICE_KEY=pdp_sa_...`, and optionally `AGENT_MODEL=` set to the name of a model published to the team. Nobody connects anything; everyone's agents are made in the team.
</Callout>

<Callout title="A platform on the same machine">
  Outside `localhost` the platform must be reached over https, because people's tokens (or the service key) travel with every request. Inside a container, `localhost` is the container itself, so a development platform at `http://localhost:8098` on your machine can't be reached from it. Use the source route below for that.
</Callout>

</Step>
<Step>

### Start it

```sh
docker compose -f compose.local.yaml up -d
docker compose -f compose.local.yaml logs app
```

The log says the database was migrated and where the server listens. If the configuration is incomplete, the server stops and the log lists every problem.

</Step>
<Step>

### Sign in

Open [http://localhost:8080](http://localhost:8080). The sign-in page lists the **Development accounts**: choose **Tim**, **Bob** or **Sally**.

<Screenshot slot="sign-in-dev" />

In Connect mode the app then shows **Connect your agents**. Select **Connect**, sign in to the platform with your own account there, and approve the app. You come back to the start page. See [Connecting your platform account](/docs/use/connect-your-platform-account). The first time, your **Assistant** is made in your personal workspace on the platform. Type a message and press Enter.

Each development account connects separately. If you connect the same platform account from two of them, they share that account's agents; connect different platform accounts to see people kept apart.

</Step>
</Steps>

To stop it, `docker compose -f compose.local.yaml down` (add `-v` to delete the database too). The agents and conversations stay on the platform.

## From source

This is the repository's development setup: the web app with hot reload on `http://localhost:5177`, the server on `127.0.0.1:5178`, and a development PostgreSQL on `127.0.0.1:55433`. Because the app runs on your machine, it can reach a development platform at `http://localhost:…`. Without a service key in `.env.local` (or with `PLATFORM_AUTH=connect`) you connect a platform account first, as above, and set `CONNECT_EMAIL_MATCH=off` for the same reason.

```sh
git clone https://github.com/ncecere/pi-agent-interface.git
cd pi-agent-interface
cp .env.example .env.local   # set PLATFORM_*, SESSION_SECRET, DEV_AUTH=true
pnpm install
pnpm db:up                   # the development PostgreSQL (compose.yaml)
pnpm dev
```

`.env.example` already has `APP_URL=http://localhost:5177` and the `DATABASE_URL` of the development database. Open [http://localhost:5177](http://localhost:5177) and sign in as Tim, Bob or Sally. To sign in as other people, set `DEV_ACCOUNTS` to a JSON array of `{"id","name","email"}`; it replaces the three accounts while `DEV_AUTH=true`.

## What to try

- Connect your platform account, then look at it in **Settings → Account**. See [Connecting your platform account](/docs/use/connect-your-platform-account).
- Send a message, then a second one while the agent is still answering: it waits its turn. **Stop** ends a reply. See [Chatting](/docs/use/chat).
- Leave a conversation while the agent works and watch it move through **Working** to **Done** in the sidebar. See [The inbox](/docs/use/inbox).
- Make an agent of your own in **Settings → My agents**. See [Agents](/docs/use/agents).
- Sign in as Bob in a private window and connect a different platform account: Bob sees none of Tim's agents or conversations.
- As Tim, open **Admin dashboard** from the menu under your name. See [Administer](/docs/administer).

## If something goes wrong

| You see | Why |
|---|---|
| The server stops with `Configuration:` and a list | A required setting is missing or unsafe. Each line names it. See [Configuration](/docs/operate/configuration). |
| "The platform doesn't offer Connect (no `connect` in /v1/auth/config)." | The platform doesn't support Connect. Use service mode. |
| "You connected … but you're signed in here as …" | The account check. Set `CONNECT_EMAIL_MATCH=off` for the development accounts. |
| "The agent platform refused this app's service key." | Service mode: the key is wrong, revoked, or its service account isn't an editor in `PLATFORM_TEAM`. |
| "The agent platform could not be reached." | `PLATFORM_URL` is wrong or unreachable from where the server runs. |
| Every agent gives the same scripted answer | No model is published (in service mode, to the team, or `AGENT_MODEL` names one that isn't), so agents use the platform's default. |
