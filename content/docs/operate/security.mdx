How Pi Agent Interface is secured depends on how it reaches the agent platform (`PLATFORM_AUTH`, see [The agent platform](/docs/operate/platform)).

- **Connect mode** (the default): the app holds each person's own platform tokens, encrypted. Each can reach only what that person may use on the platform, and the platform decides.
- **Service mode**: the app holds one powerful credential, the team service account's key, which reaches every person's agents. Most of the security is about keeping that key on the server and keeping each person to their own agents.

## Platform tokens (Connect mode)

When a person connects, the platform gives the app an access token and a refresh token for them (scope `agents`).

- **Encrypted at rest.** The server keeps them in its database (`platform_connections`), each sealed with AES-256-GCM under a key derived from `SESSION_SECRET` (HKDF-SHA256, a purpose of its own, apart from the session cookie's). The database never holds a token in the clear.
- **Never in the browser.** The browser holds only the app's session cookie. The server calls the platform for the person, and the browser is told which platform account is connected (its email or name), never a token.
- **One person's token, that person's agents.** There is no shared key. A token reaches what its person may use on the platform, and the platform enforces it. The app still refuses to rename or delete anything outside the person's own personal workspace, and provided copies can't be deleted from the app.
- **Renewed one at a time.** Access tokens are renewed shortly before they run out; the refresh token changes on every use, so a database lock lets only one renewal for a person run at a time, across replicas. A renewal the platform refuses ends the connection and the person is asked to connect again.
- **Revoked when it should be.** **Disconnect** and a refused account ask the platform to revoke the refresh token (best effort), then forget the tokens.
- **Changing `SESSION_SECRET`** makes the stored tokens unreadable. The app forgets them, and everyone connects again. To replace the secret without that, [rotate it](/docs/operate/rotating-the-session-secret): the previous secret stays in `SESSION_SECRET_PREVIOUS` for a while, and the app seals the stored tokens again with the new one.
- **The flow itself** is the authorization code flow with PKCE (S256) and a `state`, held between the redirect and the callback in a sealed, HttpOnly cookie (`__Host-pai_connect` on https) that lasts 10 minutes and is tied to the signed-in person. After connecting, people return only to a path on the app itself. An answer that names an issuer other than the platform's is refused.
- **Redirects aren't followed** in any call to the platform.
- **The metadata document is public by design.** `<APP_URL>/oauth/client-metadata.json` holds only the app's name, address, logo and callback address, and is the one thing the platform must reach without signing in.

### The account check (Connect mode)

After the platform returns a person, the app asks it who they connected (`GET /v1/me`) and compares that account's email with the person's email here, ignoring case. A mismatch would put the person's agents and conversations in someone else's workspace, so with `CONNECT_EMAIL_MATCH=require` (the default) the app **refuses** it: it asks the platform to revoke the access it was just given, keeps nothing, and shows the person:

> You connected sam.ortiz@example.com on the agent platform, but you're signed in here as priya.shah@example.com. Sign out of agents.example.com, then connect again with the same account.

The check is skipped when either side has no email address. Set `CONNECT_EMAIL_MATCH=off` only where the app and the platform use different identity providers, so the emails can't match; then nothing stops a person connecting someone else's account. See [Configuration](/docs/operate/configuration#the-agent-platform).

## The service key (service mode)

`PLATFORM_SERVICE_KEY` is read from the environment and used only by the server, for requests to the platform. It is never sent to browsers, and the server refuses to start with a platform address that isn't https (loopback excepted). Redirects from the platform aren't followed. If the platform refuses it, the log says so and people see "The agent platform refused this app's service key." To change it, set the new key and restart the server; revoke the old one on the platform once nothing uses it.

## Ownership

In Connect mode the platform decides what a person may see and use, with their own token. In service mode, every request that names an agent is checked: the agent's key on the platform must start with the signed-in person's own `u:<person>`, or the answer is "Agent not found", the same as for an agent that doesn't exist. Conversation IDs are checked for their form before anything is relayed. Events from the platform's shared event stream go only to the person whose agent they concern. This is tested in the repository's server tests. See [How people are kept apart in service mode](/docs/operate/platform#how-people-are-kept-apart-in-service-mode).

## Sessions

- **An encrypted cookie, no session store.** The session (the person's ID, name and email, a CSRF token, its expiry and the person's session version) is sealed with AES-256-GCM, under a key derived from `SESSION_SECRET` with HKDF-SHA256. It can't be read or forged without the secret, and its expiry is checked on every request.
- **The cookie** is `__Host-pai_session` on https (`pai_session` on a loopback http address): `HttpOnly`, `Secure` on https, `SameSite=Lax`, path `/`, and it lasts `SESSION_TTL_HOURS` (default 7 days). It isn't extended by use.
- **Ending sessions.** Each person has a session version. **Sign out everywhere** and a suspension raise it, which ends every session they have. The server re-reads each person's record at most every 10 seconds, so a change of role, a suspension or sign-out everywhere reaches open sessions within about ten seconds.
- **Changing `SESSION_SECRET`** signs everyone out, unless you [rotate it](/docs/operate/rotating-the-session-secret) with `SESSION_SECRET_PREVIOUS`.
- **Single sign-on** uses the authorization code flow with PKCE (S256), `state` and `nonce`, carried between the redirect and the callback in a second sealed cookie that lasts 10 minutes. After signing in, people return only to a path on the app itself, never another site.

## Writes: CSRF and origin

Every request that changes something (anything but GET, HEAD and OPTIONS) must:

- carry the session's CSRF token in `X-CSRF-Token`, and
- come from the app's own origin: an `Origin` header, when present, must equal `APP_URL`'s origin.

Otherwise it is refused: "Invalid request token or origin. Reload the page and try again." Signing out is checked the same way. The development sign-in accepts only the app's own origin.

## Limits

| Limit | Value | When reached |
|---|---|---|
| Open conversations per person | 8 | "Too many conversations are open at once. Close some and try again." Each open conversation keeps an agent awake. |
| Tabs following the inbox per person | 6 | "Too many tabs are open at once." |
| A message request | 256 KiB | Refused as too large. The web app limits messages to 32,000 characters. |
| A saved preference | `appearance` 4 KiB, `inbox` 512 KiB | Refused as too large. |
| A conversation's name | 1 to 200 characters | Refused. |

The stream limits are counted per server process.

## Headers

- Every response: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, and on https `Strict-Transport-Security: max-age=31536000; includeSubDomains`. API responses are `Cache-Control: no-store`.
- Pages: a Content Security Policy,

  ```text
  default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:;
  font-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
  ```

  so the page runs only its own scripts and talks only to its own server. Images may come from any https address, for an administrator's logo.
- Built assets under `/assets/` are cached for a year (their names change with their content); pages aren't cached.

## In the browser

Links in replies that lead to another site open through a warning that names the site (**Open external link**). On a shared browser, each person's appearance, avatar style and inbox are their own: the next person to sign in doesn't inherit them.

## Known limitations

- Access is all or nothing unless you set groups: anyone the identity provider lets sign in can use the app, as a member. Since v0.4.0 you can limit access, and choose administrators, by the provider's groups (see [Sign-in](/docs/operate/sign-in#access-and-administrators-by-group)). Groups are read when someone signs in, not during a session.
- Single sign-on is tested against an in-process provider, not against a particular product.
- The app has no rate limits of its own beyond the stream limits above.
