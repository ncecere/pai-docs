Pi Agent Interface ships as one container image: one Node.js 22 process that serves the web app and the API on port 8080, as the non-root `node` user.

## Getting the image

Since v0.2.0 the image is published: `ghcr.io/ncecere/pi-agent-interface`. The repository's release workflow (`.github/workflows/image.yml`) builds it for each release tag as a **multi-arch** image (linux/amd64 and linux/arm64), scans it for vulnerabilities, attaches SBOM and provenance attestations, tags it `vX.Y.Z` (and `latest` for final releases) and **signs** it with cosign keyless signing. The v0.2.0 image is:

```text
ghcr.io/ncecere/pi-agent-interface:v0.2.0
ghcr.io/ncecere/pi-agent-interface@sha256:b3d6103ff6a4b0149c301d78aa7a8995c6424b505b5e9a9245d2ccf5e15fb41c
```

The digest is also on the [GitHub Release](https://github.com/ncecere/pi-agent-interface/releases/tag/v0.2.0). A tag can move, so check the signature before you deploy, and deploy by digest:

```sh
cosign verify ghcr.io/ncecere/pi-agent-interface@sha256:b3d6103ff6a4b0149c301d78aa7a8995c6424b505b5e9a9245d2ccf5e15fb41c \
  --certificate-identity https://github.com/ncecere/pi-agent-interface/.github/workflows/image.yml@refs/tags/v0.2.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The identity names the workflow and the release tag that built the image, so for another release only the tag at its end changes. To build it yourself instead:

```sh
git clone https://github.com/ncecere/pi-agent-interface.git
cd pi-agent-interface
git checkout v0.2.0
docker build -t pi-agent-interface .
```

## What is in it

The build stage installs the dependencies with pnpm, type-checks, builds the web app (`dist/`, without source maps) and the server (`dist-server/`), and keeps only the server's run-time dependencies. The image is `node:22-slim`, with the operating system's security updates applied and **no npm, npx, corepack or yarn**: nothing in it runs them, and their bundled packages were the image's only Node findings in a vulnerability scan. Use `node` for everything, for example the recovery command below. It has:

| | |
|---|---|
| User | `node` (uid 1000, gid 1000) |
| Port | `8080` |
| Environment | `NODE_ENV=production`, `HOST=0.0.0.0`, `PORT=8080`, `STATIC_DIR=/app/dist` |
| Command | `node dist-server/main.js` |
| Health check | `GET /healthz` every 30 seconds |
| Also | `node dist-server/cli.js promote <email>`, the [lockout recovery](/docs/administer/first-administrator#locked-out-adminpromote) |

## Running it

```sh
docker run -d --name pai \
  -p 127.0.0.1:8080:8080 \
  --env-file pai.env \
  --read-only \
  pi-agent-interface
```

See [Configuration](/docs/operate/configuration) for `pai.env`. The server writes nothing to disk, so it runs with a read-only root filesystem (the release workflow checks the image by running it with `--read-only`), as the `node` user. On start it migrates the database, then listens, and logs where:

```text
[server] database migrated: 1, 2, 3
[server] http://0.0.0.0:8080 for https://chat.example.com · platform https://agents.example.com · team pi-agent-interface · single sign-on
```

The `database migrated` line appears only when a migration was applied. The `team` part is the service-mode team, and is empty in Connect mode.

On SIGTERM or SIGINT it stops accepting connections and waits for open ones to end before closing its database connections and exiting. Event streams stay open, so with people connected the process is usually ended by the container runtime's stop timeout instead. Nothing is lost: conversations live on the platform, and browsers reconnect on their own.

## Health

| Path | Answers | Use it for |
|---|---|---|
| `/healthz` | `{"ok":true}` whenever the server is up. It doesn't call the database or the platform. | Liveness, and the image's own health check. |
| `/readyz` | `{"ok":true}` when the database answers, else 503 `{"ok":false}`. | Readiness. |

Neither checks the agent platform: a platform outage shows up in the app as "The agent platform could not be reached.", not as an unhealthy container.

## Behind a reverse proxy

Put a reverse proxy or ingress in front that terminates TLS, and:

- **Doesn't buffer or time out the event streams.** `/api/events` (the inbox) and `/api/agents/*/threads/*/events` (an open conversation) are server-sent event streams that stay open. The app sends `X-Accel-Buffering: no` and a keep-alive comment on `/api/events` every 15 seconds; the platform sends one every 15 seconds on conversation streams. Set the read timeout to an hour or more.
- **Passes `Host` and `X-Forwarded-*` through**, and keeps `APP_URL` equal to the public address. Writes are refused unless the browser's `Origin` is `APP_URL`'s origin.
- **Leaves `/oauth/client-metadata.json` open** in Connect mode. The platform fetches it from the app's public address, and needs a plain `200` with `application/json`: no sign-in, no redirect. See [The agent platform](/docs/operate/platform#the-client-id-metadata-document).

For nginx:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off;
    proxy_read_timeout 1h;
}
```

Request bodies are small: a message is at most 256 KiB, and a person's saved inbox at most 512 KiB. nginx's default limit of 1 MiB is enough.

## Without a container

```sh
pnpm install && pnpm build && pnpm start
```

`pnpm start` serves the built web app from `dist/` and needs the same environment variables.
