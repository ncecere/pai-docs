---
title: Rotating the session secret
description: Replacing Pi Agent Interface's SESSION_SECRET without signing anyone out or making anyone connect their platform account again, using SESSION_SECRET_PREVIOUS.
---

`SESSION_SECRET` encrypts the session cookies and, in Connect mode, the platform tokens Pi Agent Interface keeps for people. Changing it alone signs everyone out, and in Connect mode everyone has to connect again, since the stored tokens can't be read with a new secret. Since v0.4.0 you can replace it without either, by keeping the old one in `SESSION_SECRET_PREVIOUS` for a while.

<Steps>
<Step>

### Set both and restart

Generate a new secret (`openssl rand -base64 48`). Set `SESSION_SECRET` to it and `SESSION_SECRET_PREVIOUS` to the old one, then restart.

```sh
SESSION_SECRET=<the new secret>
SESSION_SECRET_PREVIOUS=<the old secret>
```

`SESSION_SECRET_PREVIOUS` takes more than one secret, comma-separated, if you rotated twice before the first was dropped. Every secret must be at least 32 characters.

</Step>
<Step>

### Nobody notices

People stay signed in. A session opened with the old secret still works, and is sealed again with the new one the next time it is used.

On start, the app also seals every stored platform connection with the new secret, and logs how many it sealed and how many could not be opened with any secret (those people connect again):

```text
[server] SESSION_SECRET_PREVIOUS is set: 12 platform connection(s) sealed again with the current secret; the previous secret is no longer needed for them
```

When some could not be opened, the end of the line reads `; 2 could not be opened with any secret (those people connect again)` instead. It is safe on every start, and with two replicas starting at once.

</Step>
<Step>

### Drop the previous secret

When the log line says the previous secret is no longer needed, and after the session lifetime has passed (`SESSION_TTL_HOURS`, 7 days by default) so that the sessions of people who haven't come back have ended anyway, remove `SESSION_SECRET_PREVIOUS`.

Anyone whose session still carried the old secret signs in again. Nothing else is lost.

</Step>
</Steps>

## If the secret leaked

Rotate it the same way, but remove the previous secret as soon as the second step has run: it is the leaked one, and while it is set it still opens sessions and tokens.

## What it doesn't do

- It doesn't change `OIDC_CLIENT_SECRET` or any platform key. Those are the other side's secrets: rotate them with your identity provider or the platform.
- A database restored from before a rotation needs the secret it was sealed with: keep the old one in `SESSION_SECRET_PREVIOUS` until the restored tokens have been sealed again. See [Backing up and restoring](/docs/operate/upgrades-and-backups#backing-up-and-restoring).

## On Kubernetes

`SESSION_SECRET` is a key in the `pi-agent-interface-runtime` Secret, and the base's Deployment lists the Secret's keys one by one (`DATABASE_URL`, `SESSION_SECRET`, `OIDC_CLIENT_SECRET` and the optional `PLATFORM_SERVICE_KEY`). It has **no entry for `SESSION_SECRET_PREVIOUS`**, so a key added to the Secret alone is not passed to the app. Add the key to the Secret, and have your overlay pass it on, with a patch like the metrics component's:

```yaml
patches:
  - target:
      kind: Deployment
      name: pi-agent-interface
    patch: |-
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: pi-agent-interface
      spec:
        template:
          spec:
            containers:
              - name: app
                env:
                  - name: SESSION_SECRET_PREVIOUS
                    valueFrom:
                      secretKeyRef:
                        name: pi-agent-interface-runtime
                        key: SESSION_SECRET_PREVIOUS
                        optional: true
```

Remove the patch and the key when you drop the previous secret. Don't put either secret in the ConfigMap, which holds settings that aren't secret. See [Kubernetes](/docs/operate/kubernetes#settings-and-secrets).
