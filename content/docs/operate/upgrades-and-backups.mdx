## Upgrading

<Steps>
<Step>

### Read the release notes

Read the notes of every release between your version and the target in [Releases](/docs/releases), for new settings, migrations and anything to do by hand.

</Step>
<Step>

### Back up the database

Take a backup of the app's PostgreSQL (below). Migrations only go forward: going back to an older version past a migration means restoring this backup.

</Step>
<Step>

### Replace the image and restart

Start the new version with the same configuration. It waits for its database to answer (up to three minutes; the log says `waiting for the database…`), then applies its migrations before it listens, and logs them (`[server] database migrated: …`). If a new setting is required, the server stops and names it.

</Step>
</Steps>

People's conversations aren't affected: they live on the platform. Sessions carry on across an upgrade unless the release notes say otherwise.

### From v0.1.0 to v0.2.0

- **0.2.0 adds a database, and it is now required.** v0.1.0 had none. Set `DATABASE_URL` to an empty PostgreSQL database (see [PostgreSQL and migrations](/docs/operate/database)); the first pod to start creates the tables by applying three migrations: people, settings and preferences; people's agents; and platform connections. Set `INITIAL_ADMIN_EMAIL` so the instance gets its [first administrator](/docs/administer/first-administrator).
- **A deployment with `PLATFORM_SERVICE_KEY` set stays in service mode**, as before: nothing to change, and each person's assistant is kept, with its conversations. **Without a service key, the app now defaults to Connect** (`PLATFORM_AUTH=connect`). To keep using a service account, set `PLATFORM_AUTH=service`. The Kubernetes base sets `PLATFORM_AUTH=connect`, so a service-mode overlay must set it back.
- **Moving to Connect** is a choice, not part of the upgrade. In Connect mode people's agents live in their personal workspaces on the platform, so they start with new copies of the provided agents there. The agents made in service mode stay in the team on the platform, and the app doesn't move conversations between the two. Check first that the platform offers Connect and that the app's `/oauth/client-metadata.json` is reachable by it, as described in [The agent platform](/docs/operate/platform#connect-mode).
- **Everyone signs in again once**: sessions now carry a session version, and v0.1.0's sessions end.
- `AGENT_MODEL` is now only the fallback default: [Admin → Agents](/docs/administer/agents) sets the default model and wins.
- **The image no longer contains npm, corepack or yarn**, and is now published and signed. See [The container image](/docs/operate/container#getting-the-image).
- New settings: `DATABASE_URL` (required), `INITIAL_ADMIN_EMAIL`, `PLATFORM_AUTH`, `CONNECT_EMAIL_MATCH`, `DISABLED_FEATURES`.

See the [v0.2.0 notes](/docs/releases/v0-2-0#upgrading-from-010) for the rest.

### From v0.2.0 to v0.2.1

A patch release: replace the image and restart. There is no new migration and nothing to change by hand. `DEV_ACCOUNTS` is a new, optional, development-only setting. See the [v0.2.1 notes](/docs/releases/v0-2-1).

### From v0.2.1 to v0.3.0

Replace the image and restart. There is no new migration and no new setting. One change to startup: the app now **waits for its database**, for up to three minutes, instead of exiting and being restarted until it answers. Only "not reachable yet" errors are waited out; a wrong password or a missing database still fails at once, with the database's own message. See [PostgreSQL and migrations](/docs/operate/database#waiting-for-the-database) and the [v0.3.0 notes](/docs/releases/v0-3-0).

### From v0.3.0 to v0.3.1

Replace the image and restart. There is no new migration and no new setting. Two inbox display fixes only. See the [v0.3.1 notes](/docs/releases/v0-3-1).

## What to back up

| What | Where | Why |
|---|---|---|
| **The app's database** | PostgreSQL, `DATABASE_URL` | People and roles, instance settings (branding, agent settings, provided agents, features), everyone's preferences and inbox state, the audit log, the names of people's own agents (service mode), and in Connect mode each person's encrypted platform tokens and which agent is their copy of each provided agent. |
| **The configuration** | Your environment or secret store | Especially `SESSION_SECRET`, `OIDC_CLIENT_SECRET` and, in service mode, `PLATFORM_SERVICE_KEY`. In Connect mode `SESSION_SECRET` also opens the stored platform tokens: a database restored with a different one means everyone connects again. |
| **The agent platform** | The platform's own database and agent storage | The agents, their memory and every conversation. Back it up as its own documentation says. |

Back up the database with your usual PostgreSQL tools, for example:

```sh
pg_dump --format=custom --file=pai-$(date +%F).dump "$DATABASE_URL"
pg_restore --clean --if-exists --dbname="$DATABASE_URL" pai-2026-10-18.dump
```

Restore into a stopped app, then start it.

### What a lost database means

The agents and conversations survive on the platform. In service mode each person's agents are found again by their key when they next sign in. In Connect mode each person connects again, and the app finds their agents in their personal workspace; a provided agent's copy already there under its name is adopted, not made again. What is lost: roles (everyone is a member again, so set `INITIAL_ADMIN_EMAIL` or use [`admin:promote`](/docs/administer/first-administrator#locked-out-adminpromote) after people sign in), instance settings, preferences and inbox state, the audit log, and, in service mode, the list of people's own agents (their agents stay on the platform but no longer show in the app).

### What a lost `SESSION_SECRET` means

Everyone signs in again, and in Connect mode everyone connects again, since the stored tokens can't be read without it. Set a new one.
