---
title: PostgreSQL and migrations
description: What Pi Agent Interface keeps in its own PostgreSQL database, and how the schema is migrated when the server starts.
---

Pi Agent Interface has its own PostgreSQL database, separate from the agent platform's, named by `DATABASE_URL`. Conversations aren't in it: they live on the platform. v0.1.0 had no database of its own; v0.2.0 added it, and the app creates its tables when it starts.

## What is in it

| Table | Holds |
|---|---|
| `people` | Everyone who has signed in: their ID, email, name, role, status, session version, when they first signed in and were last seen. |
| `settings` | Instance settings as JSON: `branding`, `agents`, `provided` and `features`, with who changed each last and when. On a local `http` address in Connect mode it also holds `connect.client`, the client the app registered with the platform. |
| `user_prefs` | Each person's preferences as JSON: `appearance` (theme, accent, avatar style, typing and code wrapping) and `inbox` (pinned, snoozed, settled, archived, read). |
| `personal_agents` | Service mode: the agents people made themselves, each one's slot and the name its person gave it. The agent itself is on the platform. In Connect mode people's own agents are in their personal workspace on the platform, and this table isn't used. |
| `platform_connections` | Connect mode: each connected person's platform tokens, **encrypted** (an access token and a refresh token, and when the access token expires), and the platform account they connected (its ID, email and name), with when it was last renewed. See [Security](/docs/operate/security#platform-tokens-connect-mode). |
| `provided_copies` | Connect mode: which agent on the platform is each person's copy of each provided agent. |
| `audit_log` | The [audit log](/docs/administer/audit-log). |
| `schema_migrations` | Which migrations have been applied. |

## Requirements

PostgreSQL 17 is what the repository's development setup and its tests use. The database user needs to create tables and indexes in its database (the migrations run as it). The server opens up to 10 connections.

## Waiting for the database

Since v0.3.0 the app **waits for its database when it starts**, for up to three minutes, before it migrates and listens. A first deployment, or a node restart, often starts the app beside its database; the app no longer exits and gets restarted until the database answers. The log says `[server] waiting for the database…` once, and `[server] the database answered after Ns` when it does. It retries after half a second, with the pause growing to five seconds.

Only errors that mean the database is **not reachable yet** are waited out:

- connection refused, a host or network that can't be reached, a connection reset or closed, and timeouts (including a name that can't be resolved yet);
- the database starting up (`57P03`);
- too many connections (`53300`).

Anything else fails **at once**, with the database's own message: a wrong password, or a database that doesn't exist. Those won't fix themselves, so the app doesn't wait for them. If the database still hasn't answered after three minutes, the server stops with "The database did not answer within 180s" and the last error.

## Migrations

The server applies any migrations it hasn't applied yet **every time it starts**, before it listens, in one transaction, holding a PostgreSQL advisory lock so several servers starting together don't race. The log names what it applied: `[server] database migrated: 1, 2, 3`. The recovery command (`promote`) migrates first too.

| Version | Name |
|---|---|
| 1 | people, settings, preferences, audit log |
| 2 | personal agents |
| 3 | platform connections and provided copies (Connect mode) |

All three run on a new database, and on a database that was at version 1 or 2 only the rest are applied. They are created whichever mode the app uses, and the Connect tables aren't used in service mode. Migrations are forward-only and ship inside the server; a released one is never edited, only followed by the next. Going back to an older version past a migration means restoring a backup taken before it. See [Upgrades and backups](/docs/operate/upgrades-and-backups).

## For development

The repository's `compose.yaml` runs a development PostgreSQL 17 on `127.0.0.1:55433` (user `pai`, password `pai-local-only`, database `pai`): `pnpm db:up`. It matches `DATABASE_URL` in `.env.example`. Never use that password anywhere else.
